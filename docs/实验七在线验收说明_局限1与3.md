## 六、为什么本轮不能做到全部通过

1. **单次决策、不自动重试是既定规则。** 计划要求“一次请求一次结果、失败按回退记录、不自动重试”。模型只要选错一次动作，这一例就直接判失败，没有第二次机会；12 例 × 多个决策点，错误被放大。
2. **动作顺序是隐含约束。** 代码按“先取路线、再取建议”的必需顺序校验，但原提示词只写“仍需的 action 会在上下文中给出”，没有把“下一步唯一可执行动作”显式告诉模型。3B 模型因此频繁先调 `advice` 或先调 `route`，被校验拒绝。
3. **最终回答的复用要求高于模型习惯。** 判据要求回答必须引用已查到的建议原文，而小模型倾向概括成“建议注意体力”这类泛化表述，看起来合理但不满足可追溯要求。
4. **模型能力上限。** 本机只有 1.5B 与 3B 两个量化模型，没有真实云端 API 密钥；3B 在中文旅游语境下能理解意图，但在严格 JSON 契约与多步顺序上稳定性不足。这不是代码缺陷能完全弥补的。
5. **仍有一处链路偏差。** `family_jiuzhaigou` 的 `duration` 被解析为 2，与“玩一天”矛盾，属于意图合并逻辑的独立问题，需单独定位，不是提示词能解决。

## 七、要做到 12/12 需要什么（未实施）

- 在决策上下文里显式给出“本轮唯一允许的动作”，把顺序约束从隐含改为可见；
- 最终回答提示要求逐条引用 advice 原文，并保留现有断言；
- 定位并修正 `duration` 合并逻辑；
- 若仍不足，换更大模型（如 `qwen2.5:7b`）或按计划允许的方式重议“不自动重试”的口径。

以上任一项都会改变本轮已记录的运行结果，因此没有在本次实现中追加，避免用修改判据的方式换取通过率。
